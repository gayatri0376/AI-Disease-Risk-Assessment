1. Project Architecture & End-to-End Pipeline

HemoCare AI is a healthcare web platform that automates preliminary anemia detection from Complete Blood Count (CBC) laboratory indices. It bridges patient self-assessment, machine learning inference, clinical recommendation generation, and doctor consultation into a unified ecosystem.

System Flow:
React UI Form ➔ POST /api/screen-patient/ ➔ Django REST Framework ➔ Random Forest Classifier ➔ MySQL Storage ➔ Clinical Report JSON ➔ Interactive Visual Result

3. Machine Learning Inference Engine

Located in: backend/apps/ml_service/ and ml_model/models/

The system uses an ensemble Random Forest Classifier trained and audited across two distinct clinical tasks:

A. Task B: Binary Anemia Screening (Healthy vs. Anemia)

  • Model: Tuned Random Forest Classifier (task_b_scenario2_random_forest.joblib)
  • Operating Threshold: 0.37 (Mathematically calibrated to maximize Sensitivity/Recall)
  • Sensitivity (Recall): 100.0% (Zero False Negatives on test benchmarks — ensuring no anemic patient is missed)
  • ROC-AUC: 1.0000 | PR-AUC: 1.0000
  • Role: Decides whether patient is "Low Risk" (Healthy) or "Needs Attention" (Anemia Detected).

B. Task A: 9-Class Multiclass Hematologic Subtype Diagnosis

  • Model: Multi-output Random Forest (task_a_scenario2_random_forest.joblib)
  • Subtypes Classified:
    1. Healthy (Non-Anemic)
    2. Iron deficiency anemia
    3. Normocytic normochromic anemia
    4. Normocytic hypochromic anemia
    5. Other microcytic anemia
    6. Macrocytic anemia
    7. Thrombocytopenia
    8. Leukemia
    9. Leukemia with thrombocytopenia
  • Role: Calculates calibrated class probability distributions and characterizes the specific underlying etiology.

6. MySQL Database Schema & Demonstration Queries

Database: anemia_system (MySQL Port: 3306)

A. Core Database Tables

  • screening_patient: Patient profiles (name, email, age, gender, weight, height).
  • screening_bloodreport: 14 CBC parameters, RDW, and symptoms.
  • screening_screeningresult: AI screening predictions, confidence scores, and raw JSON.
  • screening_diagnosisreport: Multiclass subtype diagnoses and limitations.
  • screening_recommendation: Generated medical actions and priority tags.
  • screening_doctor: Verified doctor directory for consultations.
  • screening_appointment: Consultation bookings between patients and doctors.
  • auth_user: Secure Django user table with PBKDF2 hashed passwords.

B. Key SQL Queries for Viva & Evaluation

Query 1: View Clean Patient Screening Report with Diagnosis

USE anemia_system;

SELECT 
    p.name AS Patient_Name,
    p.gender AS Gender,
    b.hemoglobin AS Hemoglobin_g_dL,
    b.mcv AS MCV_fL,
    r.prediction_label AS Screening_Status,
    CONCAT(ROUND(r.confidence * 100, 1), '%') AS Confidence,
    d.interpretation AS AI_Interpretation
FROM screening_screeningresult r
JOIN screening_screeningrequest req ON r.request_id = req.id
JOIN screening_bloodreport b ON req.blood_report_id = b.id
JOIN screening_patient p ON b.patient_id = p.id
JOIN screening_diagnosisreport d ON d.result_id = r.id
ORDER BY r.id DESC;

Query 2: Extract Subtype Probabilities from JSON

SELECT 
    id AS Result_ID,
    prediction_label AS Status,
    raw_output->>'$.task_a.predicted_diagnosis' AS Specific_Diagnosis,
    raw_output->>'$.task_b.probability_healthy' AS Healthy_Probability,
    raw_output->>'$.task_b.probability_anemia' AS Anemia_Probability
FROM screening_screeningresult
ORDER BY id DESC LIMIT 5;

Query 3: View Booked Appointments

SELECT 
    id,
    patient_name,
    doctor_name,
    date,
    time,
    status,
    why AS Consultation_Reason
FROM screening_appointment
ORDER BY id DESC;

Query 4: View Registered Patients and Demographics

SELECT 
    id,
    name,
    email,
    age,
    gender,
    weight AS Weight_kg,
    height AS Height_cm
FROM screening_patient
ORDER BY id DESC;
